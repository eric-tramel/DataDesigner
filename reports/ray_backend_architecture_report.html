Architecture and Performance Report

Ray In-Memory Backend for DataDesigner

This report summarizes the implementation, architectural decisions, benchmark results, and remaining optimization work for adding an optional Ray-backed execution path that accepts Ray-resident inputs and returns Ray-resident outputs without changing default local behavior.

worktree: /Users/eric/src/DataDesigner-ray-backend branch: feat/ray-backend date: 2026-04-23 Ray: 2.55.1 Python: 3.13

Executive Summary

Implemented

A new optional RayBackend execution path plugs into DataDesigner through a small backend protocol. Users can pass a Ray Dataset or Ray ObjectRef sequence as input_dataset and receive either a Ray Dataset or Arrow ObjectRefs back.

Default Behavior

The local path remains the default. Ray is imported lazily and is only installed through data-designer[ray]. Without a backend, create() keeps the existing local artifact-backed behavior.

Performance Takeaway

The 256-row OpenAI run shows an effective-concurrency win, not a pure Ray-only engine speedup. The local path used the current default create() behavior, while Ray used block-level parallelism plus async worker execution.

Important fix from benchmarking: running local seeded jobs before Ray jobs initially exposed a serialization failure from cached DuckDB connections inside seed readers. The Ray backend now clones seed readers into clean unattached worker copies before sending them to Ray workers.

Layering and Modularization

The implementation preserves the repository's structural layering: interface depends on engine, engine depends on config, and config remains independent of both. Ray is an optional integration owned by the interface package, not a dependency of config or engine.

Execution Architecture

The local path still compiles config, builds artifacts, profiles the output, and returns a local DatasetCreationResults. The Ray path converts the input data plane into Ray Data blocks, executes each block with worker-local engine resources, and keeps the result in Ray.

Ray Worker Boundary

The most important architectural boundary is the worker payload. Anything sent through Ray must be serializable and should be data-like. The backend now copies only the necessary interface state and removes attachment state from seed readers before serialization.

Serialization rule: worker options must contain plain config/state, not open handles. The benchmark found DuckDB connections retained inside seed readers. The fix clones readers and clears source, secret_resolver, and _duckdb_conn before Ray sees them.

Public API Shape

The intended user path is simple: existing local users do nothing. Ray users install the extra, initialize or connect to Ray, and pass the backend plus an in-memory Ray input handle. 

import ray
from data_designer.interface.data_designer import DataDesigner
from data_designer.integrations.ray import RayBackend

ray.init(address="auto")  # or an existing local/session cluster

designer = DataDesigner(
    artifact_path="artifacts",
    model_providers=[...],
    backend=RayBackend(batch_size=1024),
)

results = designer.create(config_builder, input_dataset=ray_dataset)
ray_dataset_out = results.load_dataset()

Supported input forms are Ray Dataset, Arrow ObjectRefs, and pandas DataFrame ObjectRefs. Supported output forms are Ray Dataset and Arrow ObjectRefs.

Why Performance Can Differ

Ray does not make gpt-4.1 generate tokens faster, and it does not reduce the number of model calls required by the recipe. Any speedup has to come from the orchestration around those calls: how many requests are in flight, how much work is serialized through one driver process, and how much local artifact work is on the critical path.

The unit of parallelism changes

The local benchmark exercises the current default DataDesigner.create() path in one process. The Ray benchmark converts the 256 requested rows into a Ray Dataset, partitions it into 16 batches of 16 rows, and runs map_batches(). Each Ray worker constructs its own DatasetBuilder with use_async=True for that block.

LLM latency is overlapped

The recipe has three model-backed columns per row, so 256 rows imply roughly 768 OpenAI requests before retries or implementation details. The Ray metrics reported 770 successful gpt-4.1 requests. Ray wall time was 304.590s, while summed worker elapsed time was 1,002.803s, which means the run overlapped about 3.29 worker-seconds per wall-clock second. That overlap is consistent with the observed 2.96x wall-clock speedup on a 4-CPU local Ray instance.

Ray adds fixed costs

Each Ray block crosses a serialization boundary and currently rebuilds temp artifact storage, resource providers, model registries, seed-reader state, and a dataset builder. That fixed setup cost is why Ray is expected to lose on sampler-only or tiny jobs. It only becomes attractive when model/network latency is large enough to hide that scheduling and setup overhead.

The benchmark is not a pure engine microbenchmark

The local create() path writes artifacts, reloads the generated dataset, and runs profiling. The Ray backend currently uses preview-style block execution and returns Ray-resident outputs; distributed profiling is still future work. So the measured number is best read as "current local user path versus experimental Ray data-plane path", not as an isolated comparison of identical inner loops.

Provider limits decide the ceiling

More Ray workers increase request concurrency, but throughput stops improving once the OpenAI account, model endpoint, network, or DataDesigner model-config concurrency limits become the bottleneck. A robust benchmark suite should sweep batch_size, Ray worker count, and model max_parallel_requests, then report request rate, token rate, retry/throttle counts, and output quality alongside rows/sec.

Interpretation guardrail: the 2.96x result is a real end-to-end result for this branch and recipe, but it should not be generalized as "Ray is 3x faster." It says that this OpenAI-heavy job had enough independent network-bound work for Ray's block-level concurrency to overcome its setup overhead in this local test. The next correctness/performance phase should add an apples-to-apples local async baseline and repeated runs with confidence intervals.

What We Learned

Ray helps when work is large enough

The 256-row OpenAI benchmark is the clearest signal so far: for a recipe with three model-backed columns, the Ray path was 2.96x faster than the current local default path on a local 4-CPU Ray instance. The likely mechanism is not faster model execution; it is overlapping independent OpenAI calls across Ray blocks and async workers once model work dominates scheduling overhead.

State boundaries matter

DataDesigner has stateful readers and resource providers optimized for a local process. Ray forces us to separate configuration from execution state. The seed-reader clone fix is the first concrete example of the right architectural direction.

Returning refs works

The Ray backend can return Arrow ObjectRefs, so the output can remain in Ray object store instead of materializing on the driver. The result dataset is rebuilt from those materialized refs, so later load_dataset() calls do not re-run generation.

Order semantics differ

Ray Data does not guarantee the same output ordering as the local path under all execution plans. If stable order is required, the backend should inject and preserve an internal row id.

Current Limitations

  1. Per-block setup cost: each Ray block currently creates temp artifact storage, resource providers, registries, and a DatasetBuilder.
  2. Per-block model health checks: workers may repeat checks that should be a driver preflight or cached per worker.
  3. No actor reuse: map_batches uses a function. A callable class or actor-style execution could reuse model clients and resource setup across blocks.
  4. Profiler artifact scope: Ray results now expose bounded worker profile summaries, trace events, and worker-local throttle snapshots through load_analysis(). Full local-style DatasetProfilerResults still requires materializing the dataset on the driver and remains unsupported for Ray-resident outputs.
  5. Automatic ordering: explicit order_column sorting is supported, but hidden row-id injection for automatic preserve_order=True is still future work.
  6. Seed configs without input datasets: Ray now rejects this unsafe mode before execution. Partition-offset-aware seed readers remain future work; use in-memory Ray inputs for seeded Ray jobs today.
  7. From-scratch partitioning: ray.data.range(num_records) needs explicit block planning for high throughput.
  8. Processor side effects: unsafe processors are now rejected by default, but first-class distributed side-effect semantics are not implemented.
  9. Trusted-cluster boundary: provider config and secret resolvers are serialized to workers. The supported deployment assumption is a trusted single-tenant Ray cluster or equivalent platform isolation.

Robustness and Correctness Hardening Plan

The A-F implementation push keeps distributed correctness ahead of throughput optimization. The matrix below tracks the current implementation focus and acceptance bar for each phase without treating benchmark smoke results as production-readiness evidence.

Phase Status Scope Acceptance Criteria
Phase A: Data Semantics Contract Partly done Stabilize the logical row contract for Ray inputs and from-scratch generation. Completed pieces: supported pandas refs, Arrow refs, and Ray Dataset inputs preserve row/schema behavior in tests; explicit order_column sorting can restore order; unsafe seed-config batching is rejected. Remaining: automatic hidden row-id injection for preserve_order=True, partition-offset-aware seed configs without input_dataset, and deterministic seeding independent of Ray block order, worker identity, or scheduling timing.
Phase B: Worker Boundary Done for current scope Treat the Ray worker payload as a serialization boundary. Seed readers, config builders, model configs, secret resolvers, processors, and resource handles must be classified as serializable data, worker-local runtime state, or explicitly unsupported. Ray execution succeeds after a local seeded run in the same process; seed readers sent to workers contain no live DuckDB connections, file handles, or attached source state; unsupported objects fail during driver preflight before any Ray task is launched. The markdown recipe exercise confirms unsupported seed configs are rejected before Ray batching.
Phase C: Processor Policy Guard done Define processor side-effect semantics. Completed pieces: the backend allows the distributed-safe drop_columns processor path, rejects other processors by default before Ray tasks launch, and exposes an explicit experimental allow_unsafe_processors=True bypass. Remaining: processor metadata or registration should declare ray_safe, requires_global_order, and side-effect behavior so safe processors can be admitted without hard-coded policy.
Phase D: Error and Metrics Surface Metrics and bounded artifacts done Worker metrics aggregation now uses a Ray-side actor that returns compact usage, row-count, block-count, failed-block, elapsed-time, model-usage summaries, per-worker profile summaries, bounded trace events, and worker-local throttle snapshots to the Ray result object. Zero-row worker metrics remain zero instead of falling back to requested driver row counts. Remaining: broader Ray serialization, object-store, cancellation, and worker exceptions should carry richer task/block context. Validation counts, retry attribution, and full local-style profiler reports remain future work rather than part of the bounded Ray-native artifact channel.
Phase E: Optional Extra Guarantees Done Preserve no-Ray installs. Imports outside data_designer.integrations.ray must not import Ray, require Ray dependencies, or slow normal startup. The data-designer[ray] extra remains the only supported installation path for Ray execution. A clean environment without Ray can import data_designer, build configs, and run local paths; attempting to construct or use RayBackend without the extra gives a targeted installation message; import-time profiling stays within the existing fast-import budget.
Phase F: Test Matrix Done for experimental PR The correctness-first test matrix now covers local versus Ray Dataset versus Arrow ObjectRefs, seeded versus from-scratch generation, one block versus many blocks, pandas and Arrow-backed inputs, pure and rejected processors, success and failure paths, Ray installed and Ray absent. Remaining for production: expand from fake Ray/test doubles into recurring real-Ray smoke coverage, repeated OpenAI benchmark runs, and an apples-to-apples local async comparison.
Sequence constraint: performance work should not mask correctness gaps. Worker reuse and block planning are high-value optimizations, but they should follow the remaining row-id, seed-offset, error-context, global-throttling, and processor-metadata gates above. Metrics aggregation, bounded Ray-native observability artifacts, no-Ray optional import behavior, Arrow-ref materialization, seeded-mode rejection, and zero-row metrics are no longer open roadmap items in this experimental branch.

Optimization Roadmap

Phase 1: Correctness Hardening

  • Done: reject seed configs without input_dataset instead of duplicating early rows across Ray batches.
  • Done: rebuild Arrow-ref result datasets from materialized refs so load_dataset() does not re-run generation.
  • Done: aggregate Ray worker metrics and preserve zero-row worker totals.
  • Done: expose bounded Ray worker profile summaries and trace artifacts without driver dataset materialization.
  • Done: reject unsupported processors by default and cover the bypass path.
  • Done: add tests for explicit ordering, ObjectRef input formats, same-process local-then-Ray execution, optional-extra behavior, and metrics aggregation.
  • Remaining: add automatic hidden row-id preservation for Ray inputs and from-scratch generation.
  • Remaining: add partition-offset-aware support for seed configs without requiring input_dataset.
  • Remaining: preflight model health checks on the driver and skip repeated worker checks.

Phase 2: Worker Reuse

  • Use Ray Data callable classes for map_batches so setup runs once per worker.
  • Reuse model client pools and resource providers per worker.
  • Replace temp artifact storage with an in-memory preview artifact abstraction where possible.
  • Broadcast immutable compiled configs instead of deep-copying builders repeatedly.

Phase 3: Cluster Throughput

  • Expose override_num_blocks / block planning controls.
  • Coordinate provider throttling globally across Ray workers.
  • Support actor placement, CPU/GPU/resource labels, and autoscaling-friendly defaults.
  • Done: extend Ray-native trace collection beyond the compact execution metrics actor with bounded worker events.
Global throttling design note: current Ray observability surfaces worker-local ThrottleManager snapshots so rate-limit behavior is visible after a run. Enforcing a true job-level provider cap remains issue #13 because each worker constructs its own ModelRegistry and ThrottleManager through create_resource_provider(). The integration point is to inject an actor-backed throttle manager or proxy before ModelRegistry registers model facades, so ThrottledModelClient acquire/release calls coordinate through one Ray-side state holder.

Recommended Next Implementation Steps

  1. Turn the benchmark script into a repeatable suite. The OpenAI benchmark now lives in scripts/benchmarks/benchmark_ray_openai.py; next, add multiple iterations, confidence intervals, machine-readable historical outputs, and CI-safe dry-run modes.
  2. Implement partition-offset-aware seed support. Either teach seed readers to accept per-block offsets/selections or compile seeded jobs into explicit Ray input datasets before worker mapping.
  3. Make block planning explicit. Add num_blocks or target_block_size options to RayBackend and use Ray APIs to avoid accidental tiny blocks.
  4. Switch to worker setup reuse. Implement a Ray Data callable class that constructs model clients and DataDesigner resources once per worker process.
  5. Extend the distributed metrics channel. Add validation counts, retry attribution, object-store events, and cancellation context on top of the current worker usage, failed-block, trace, profile, and throttle-snapshot aggregation.

Bottom Line

The architecture is now in the right shape: Ray is an optional interface-level backend, not a cross-cutting dependency, and the engine remains reusable through an explicit async execution selector. The current Ray path proves the in-memory contract end to end, but it is still a first functional backend, not an optimized distributed runtime. The highest-leverage next step is partition-offset-aware seeded execution, followed by worker reuse, explicit partition planning, and richer distributed tracing/profiling.
